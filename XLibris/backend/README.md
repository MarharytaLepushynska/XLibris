# XLibris
## Опис бізнес-правил та матриці переходів станів
### BookRequest
* Користувач не може створити BookRequest на свою ж книгу
* Користувач не може створити BookRequest на книгу в статусі BLOCKED
* Користувач не може створити BookRequest на книгу, якщо в нього вже є існуючий BookRequest для цієї книги
* Не можна видалити неіснуючий BookRequest
* Якщо власник переводить книгу в статус BLOCKED, всі BookRequest на неї переходять в статус CANCELLED
* Позичальник може підтвердити/скасувати BookRequest тільки після підтвердження власника

**Матриця переходів**
- PENDING -> APPROVED
- PENDING -> REJECTED
- PENDING -> CANCELLED
- APPROVED -> FULFILLED
- APPROVED -> REJECTED
- APPROVED -> CANCELLED

### User
* Не можна побачити контактну інформацію користувача, якщо у вас з ним немає спільного Loan
* Лише адміністратор може редагувати рейтинги користувача
* Користувача може видалити або він сам або адміністратор
* Контактну інформацію користувача може редагувати або він сам або адміністратор

### Book
* Користувач може створити книгу, при її створенні книги їй автоматично присвоюється новий ID та статус AVAILABLE.
* Оновлення та видалення книги можливі лише для існуючої книги.
* Якщо BookRequest переходить у статус FULFILLED, книга переходить у статус BORROWED.
* Якщо книга переводиться у статус BLOCKED, публікується подія про блокування книги.
* При зміні статусу BookRequest система оновлює статус пов'язаної книги.

**Матриця переходів**
- AVAILABLE -> BLOCKED
- BLOCKED -> AVAILABLE
- AVAILABLE -> BORROWED
- BORROWED -> AVAILABLE

### Feedback

* Користувач не може залишити відгук самому собі.
* Feedback можна створити лише після завершення оренди, коли відповідний Loan має статус RETURNED.
* Feedback можуть залишати лише учасники відповідного Loan один про одного: власник про орендаря та орендар про власника.
* Один користувач не може повторно залишити Feedback для одного й того самого Loan.
* При створенні Feedback йому автоматично присвоюється унікальний ID та час створення.
* Після повернення книги власник та позичальник отримують сповіщення з пропозицією залишити відгук один про одного.

### Notification

* При створенні Notification йому автоматично присвоюється унікальний ID та час створення.
* Системні сповіщення можуть створюватися асинхронно у відповідь на доменні події інших модулів.
* Після створення Loan власник книги та позичальник отримують сповіщення про створення позики та очікувану дату повернення.
* Після повернення книги власник та позичальник отримують сповіщення про завершення позики.
* Після повернення книги власник та позичальник отримують окреме сповіщення з пропозицією залишити Feedback.
* Після створення Report сповіщення отримує лише користувач, який подав скаргу.
* Після вирішення Report сповіщення про рішення модератора отримують користувач, який подав скаргу, та користувач, якого стосується скарга.
* Після відхилення Report сповіщення отримує лише користувач, який подав скаргу.

### Loan

* При створенні Loan йому автоматично присвоюється унікальний ID, дата створення та статус ACTIVE.
* Власник книги та позичальник не можуть бути однією й тією самою особою (заборонено брати в оренду власну книгу).
* Очікувана дата повернення книги не може бути в минулому часі.
* Позику створюється автоматично на основі погодженого запиту, коли відповідний BookRequest переходить у статус FULFILLED.
* Позику можна позначити як повернуту лише якщо вона існує та перебуває в активному або протермінованому стані.
* При поверненні книги позиці фіксується фактична дата повернення і статус змінюється на RETURNED.
* Якщо поточна дата перевищує очікувану дату повернення, а книгу не повернуто, статус позики вважається протермінованим (OVERDUE).

**Матриця переходів**
- ACTIVE -> RETURNED
- ACTIVE -> OVERDUE
- OVERDUE -> RETURNED

### Report

* При створенні Report йому автоматично присвоюється унікальний ID, дата реєстрації та статус PENDING.
* Скарга може створюватися як у межах конкретної оренди, так і автономно щодо профілю чи поведінки користувача.
* Якщо скарга створюється в межах оренди, подати її може лише учасник цієї оренди (власник або позичальник).
* Користувач не може подати скаргу на самого себе.
* Оновлювати деталі скарги (заголовок, тип, опис, докази) можна лише для скарги, що існує і тільки до початку її модерації.
* Модератор може взяти скаргу в обробку, перевівши її у статус IN_REVIEW.
* Вирішення скарги модератором переводить її у фінальний статус RESOLVED (із зазначенням вердикту та коментаря) або REJECTED (із зазначенням причини відхилення).

**Матриця переходів**
- PENDING -> IN_REVIEW
- IN_REVIEW -> REJECTED
- IN_REVIEW -> RESOLVED
